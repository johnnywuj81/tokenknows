关于本书

本书的内容，不是事后写出来的。

2026 年 5 月到 8 月，我和另外四位工程师用十二周时间，从零搭建了一个面向 AI 研发团队的私有化知识平台——TokenKnows。在这十二周里，我们的每一次代码提交、每一段架构讨论、每一个 Prompt 迭代、每一次故障复盘，都被产品本身记录、识别、归档。

十二周结束时，TokenKnows 实例里沉淀着 6,000 多条研发事件、120 多份生成文档（周报、技术方案、ADR、故障复盘）。我从中挑出 11 条主线，请产品再帮我整理成章节草稿，自己改写润色，配上反思与图示，就有了你手里这本书。

所以本书的每一段，几乎都能在边栏注释里追到一个**真实**的源头——某个 PR、某段对话、某次评审、某次半夜的争论。我没有发明任何"教学情节"——所有"我们"做过的事，产品都还记着。

这是一本被自己造出来的书。

——John，2027 年春，于杭州

第四章 · LLM 抽象层 74

第三周一个周二的晚上，alice 在内部 Slack 里发了一段话：「我们到底要不要直接接 LangChain？再不决定下周的活就开不动了。」

▌ 原始对话
讨论可追溯到 Slack #tokenknows-dev 频道 2026-05-26 22:47
→ slack_msg_b7f3a1

那个晚上之前，我们已经为这件事来回三周了。

▌ 项目周报
Week 5 周报「关键决策」段落记录了这一争论的两端立场
→ asset_wkr_w5_v3
bob 站在"直接用 LangChain"的一边——它有现成的 chain、agent、tool 调用抽象，社区生态最大，最不容易出错。我和 carol 站在另一边：自研一个轻量 LLM Gateway——理由更多是预感而非可论证，"它好像不适合我们要做的事"。

真正让我们决定不用 LangChain 的，是 alice 那晚补的一句话——

我们的核心不是"调用 LLM 完成任务"，
而是"路由不同任务到不同模型"。
LangChain 是前者的工具。

这句话戳到了关键。

▌ 架构决策记录
ADR-003 第 3 节"备选方案对比"明确列出 LangChain / LiteLLM / 自研三选项
→ asset_adr_003_v2
TokenKnows 要做的是一件具体的事：把数据接入、价值识别、文档生成、脱敏判断这六类任务，分别路由到不同的模型与服务商。每个任务对模型的要求不同——价值识别可以用轻量本地模型，文档润色需要 Claude 级别的能力，脱敏判断要求模型完全离线。这不是一个"chain"问题，是一个"adapter + router"问题。

LangChain 当然可以实现这个，但它的 chain / agent 抽象会绕一层。更要命的是，它的依赖树深、版本变化快、内部 API 不稳定——而 TokenKnows 要面对的是私有化客户，需要数年级别的 ABI 稳定与可审计性。

▌ PR 讨论
PR #128 的评论区有详细的依赖审计讨论，最终 16 个依赖被裁减到 4 个
→ pr_128_comments

第四章 · LLM 抽象层 75

第二天 PR #135 由 dave 起的草。

▌ Pull Request
PR #135 「refactor: introduce BaseAdapter」
→ github/pr_135
一个接口，两个方法，BaseAdapter 抽象类：

# tokenknows/llm_gateway/base.py class BaseAdapter(ABC): provider: str is_cloud: bool # True for cloud, False for local async def generate( self, messages: list[LLMMessage], options: LLMOptions ) -> LLMResponse: ... async def stream( self, messages: list[LLMMessage], options: LLMOptions ) -> AsyncIterator[str]: ...

就这些。

▌ 技术方案
Tech Design「LLM Gateway v1」§3.1 记录了"刻意保持接口窄"的设计原则
→ asset_techdesign_llm_gw
那种克制是有意识的。我们清楚，每加一个方法、每加一个参数，将来都会变成兼容性债务。所以最早的那一版只有两个方法、四个字段，连流式响应的细粒度都没有暴露。

三周后，Anthropic、OpenAI、Ollama、vLLM 四个适配器全部就位。每个适配器大约 80 行代码——远比我们预想的要简单。抽象层不需要复杂，需要的是稳定。

▌ 周报片段
Week 14 周报回顾："早期定下来的窄接口，让后面三周的开发几乎没有意外"
→ asset_wkr_w14_v1

六个月之后回看，这是 TokenKnows 整个项目里少数几个"做对了"的决定之一。客户端切换模型不需要重启、不需要改业务代码；新加一个 provider 只要写一个 80 行的 adapter；甚至客户自己的 IT 团队都能写一个内部模型的 adapter——因为接口窄到他们一眼就能看懂。

但我得诚实地补一句：我们当时没有任何把握说这是"对的"。决定靠的是那个周二晚上的一句话，加上四个人一起的直觉。

▌ 月度复盘
第二月复盘中，alice 写道："其实我们当时怕极了——万一 LangChain 才是对的呢？"
→ asset_retro_2026_06

下一节，我们会回到那个抽象层，看它在真实压力下如何演化——具体来说，是当 alice 突发奇想要让"价值识别"也能切换模型的那一天。

流程大致是这样的：

  1. 在 TokenKnows 里选定"主题" → 系统按主题相关性聚合事件
  2. 系统生成"章节草稿" + 完整证据链（每段都标注来自哪个资产）
  3. 我（人）做主编：增减取舍、加入个人视角与情绪、润色叙事节奏
  4. 技术审校 + 客户脱敏审查 + 法务版权核对
  5. 出版社编辑做最后语言润色

边栏注释里的每一条 → source_id 都对应着实例里一条真实记录。读者读完一段觉得疑惑，可以扫码到 TokenKnows 的公开版本（脱敏后的）看原文。这是任何"事后写出来的"书都做不到的可信度。

十二周的项目，最终变成 380 页的书。
但更重要的是：这本书的每一句话，都有出处。
