## 3. Sprint 排期建议（2 人 × 2 sprint）

### Sprint 1（2 周）· 后端地基

| 工程师 A（后端核心） | 工程师 B（后端 + API） |
|---|---|
| T26 DB Schema | T27 APScheduler 接入 |
| T29 cron_evaluator | T28 Rule CRUD + Seeder |
| T30 Dispatcher（启动）| T32 REST API（OpenAPI 先行）|
| T31 withdraw_resolver | T32 SSE 集成 |

**Sprint 1 结束验收**：
- 4 条默认规则已 seed 到 DB
- APScheduler 6 个 jobs 跑起来无错误（1 小时观察）
- 模拟周一 09:00 → 端到端 fired → asset 入库（含 trigger_meta）
- OpenAPI 完整，前端可同步开工

### Sprint 2（2 周）· 前端 + 端到端打磨

| 工程师 A | 工程师 B |
|---|---|
| T33 Tab 静态版（用 MSW mock） | T34 Notifications + Badge |
| T33 接真后端 | T35 Onboarding Wizard |
| T30 / T31 收尾（错误处理 + 集成测试） | 端到端 SSE 联调 |
| 性能基线验证（Proposal 附录 B） | 部署到 staging |

**Sprint 2 结束验收**：
- 真实试点项目接入 30 天
- ≥ 4 份周报自动产出（每周一）
- 0 次误触发账单异常
- 撤回窗口实测用户取消率 < 10%
- 单测覆盖率 backend ≥ 80% / frontend ≥ 70%

---

## 4. 验收标准（v0.4.0 整体 Done）

| 维度 | 标准 |
|---|---|
| 调度准确性 | 周一 09:00 ±2 分钟内触发 |
| 撤回精确性 | 用户取消后 LLM 一定不被调用 |
| 数据完整性 | 每份自动生成 asset 必有完整 trigger_meta |
| SSE 端到端 | 浏览器订阅 → 5 个事件类型都能正确推送 |
| 单测 | backend ≥ 80%；frontend ≥ 70% |
| 性能 | cron_evaluator 单次扫描 < 200ms；APScheduler 在 1000+ 次执行下无丢失 |
| 用户体验 | "首次启用 → 第一份自动周报" 走通 < 1 小时（含等待）|

## 5. 不在范围（v0.4.0 不做）

- **事件触发**（GitHub webhook / IM signal）→ v0.4.1
- **阈值触发**（累积 50 章 → book / IM 信号 → skill）→ v0.4.2
- **规则编辑器**（builder 模式 / 自定义规则）→ v0.4.3
- **配额管理**（月 token 上限 / 仪表盘）→ v0.4.4
- **多实例调度**（PostgreSQL JobStore）→ v0.5
- **邮件通知**（仅 web SSE 即可）
